# 2026-08-18 工作日志：延迟生效配置的回显与查询接口设计

## 今日概览

围绕某内部系统的延迟生效配置整理联调方案：用户可以为配置变更指定未来生效日期，在计划日期到来前继续使用当前值，到期后再由任务统一应用。本日重点明确了详情页与编辑页的回显契约，并评估是否需要把“当前生效数据”和“待生效草稿”拆成两个查询接口。最终选择暂不拆分，由同一响应承载两层数据。公开版本只保留通用契约和验证方法，已移除真实业务名称、字段名、接口路径和内部模块关系。主路径尚未完成端到端验证。

## 完成事项

- 整理立即保存、计划保存、到期应用和取消待生效变更等测试路径。
- 核对快照序列化方案与现有对象映射约束。
- 明确详情页读取当前数据，编辑页优先读取待生效草稿。
- 评估单接口双层数据与双接口设计的维护和性能差异。
- 记录定时任务无法即时观察应用结果时的验证方式。
- 保留旁路更新与未落地草稿并存时的待确认事项。

## 问题与解决

### 同一查询如何支持详情与编辑回显

- **现象**：详情页和编辑页查询同一条记录，却需要展示不同版本的数据。
- **分析**：记录同时存在“当前生效值”和“待生效快照”。两处页面不是查询不同对象，而是从同一响应读取不同层级。
- **处理**：约定详情页只读取当前字段；编辑页在存在待生效快照时优先使用快照，否则回退到当前字段。
- **验证**：接口契约已整理，前端实际回显结果待联调确认。

### 是否需要拆分为两个查询接口

- **现象**：单一响应同时包含当前数据和草稿数据，容易产生职责不够单一的疑虑。
- **分析**：拆分接口能提升语义清晰度，也便于未来独立授权；但当前草稿仅在单条详情查询中返回，多数记录没有草稿，性能收益有限。贸然拆分还会扩大前后端契约改动范围。
- **处理**：当前迭代保留单接口双层响应，在服务端统一控制草稿是否可见；若后续出现独立权限或明显负载问题，再评估拆分。
- **验证**：设计决策已确认，实际数据量和权限需求仍需在后续迭代观察。

### 到期应用无法立即观察

- **现象**：把计划日期调整到当前日期后立即查询，当前配置仍未变化。
- **分析**：修改计划日期只代表记录满足扫描条件，必须等待调度任务真正执行后才会应用。
- **处理**：测试流程明确区分“数据已到期”和“任务已执行”；开发环境可使用受控的任务触发方式验证，其他环境按调度周期观察。
- **验证**：测试说明已补充，任务应用结果待验证。

## 技术记录

计划保存的核心语义可以抽象为：

```text
未指定未来生效时间：
  立即更新当前数据，并清理尚未应用的草稿

指定未来生效时间：
  当前数据保持不变，只保存计划时间和待生效快照
```

查询响应可用以下通用结构理解，字段仅用于说明分层，不对应真实接口：

```json
{
  "current": {
    "displayName": "当前值",
    "enabled": true
  },
  "effectiveDate": "未来日期",
  "pending": {
    "displayName": "待生效值",
    "enabled": false
  }
}
```

快照序列化应复用项目统一的对象映射规则，特别关注日期格式、忽略字段和敏感字段。共享序列化组件需要保证线程安全，不应在每次请求中重复创建重量级对象。
