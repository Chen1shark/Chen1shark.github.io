## 问题与解决

### 导入记录缺少编辑和详情能力

- **现象**：导入生成的计划记录在列表中通常不能直接编辑，也看不到与手工规则相同的详情。
- **分析**：导入和手工配置走不同的数据链路。导入侧更偏向批量生成结果，不一定保存可复用的周期规则明细，因此无法直接套用手工规则的编辑页面。
- **处理**：先按接口职责区分导入批次、规则配置和按日展开的计划记录，不把名称相似的接口视为同一资源。
- **验证**：后端数据链路已静态核对；前端按钮显隐逻辑待确认。

### 现场位置被误认为到岗核验或时长来源

- **现象**：现场位置信息容易被理解为另一种到岗方式，甚至被认为会直接参与时长计算。
- **分析**：到岗核验侧校验允许地点，位置采集侧接收坐标并解析业务位置，主要服务于调度和可视化。两者的数据来源、频率和业务用途不同。
- **处理**：按职责拆分位置采集、到岗核验和时长计算链路，避免排障时互相替代。
- **验证**：服务端代码已静态核对；客户端定位实现待确认。

### 锁的使用方式容易混淆

- **现象**：方法级锁注解、显式业务锁和普通参数校验容易被当成同一种机制。
- **分析**：方法级锁适合防止同一业务键的重复提交，方法结束即可释放；业务单据状态锁需要覆盖状态修改和事务提交窗口，避免锁先释放、事务后提交造成并发穿透。
- **处理**：按“防重复调用”和“保护同一实体状态流转”两类目标选择锁，并确保同一业务实体使用稳定一致的锁键。
- **验证**：实现方式已静态核对，未执行并发测试。

### 主动申报与系统生成数据混淆

- **现象**：多个入口名称相近，难以判断哪些数据由系统生成，哪些数据由用户主动申报。
- **分析**：系统生成数据通常基于计划和实际结果自动产生；主动申报则围绕业务项目建立周期汇总与日明细，并可能进入审批流程。两者在来源、状态和用途上不同。
- **处理**：从接口入口开始，按校验、加锁、流程创建、周期对象组装和日明细写入的顺序跟读代码。
- **验证**：调用链已静态梳理，尚未编译或联调。

## 技术记录

主动申报链路可抽象为：

```text
接收申报请求
  -> 按业务周期、业务对象和权限范围生成锁键
  -> 校验是否存在重复申报
  -> 判断能否复用已有流程
  -> 必要时启动审批流程
  -> 创建周期汇总记录
  -> 按日期写入明细
  -> 更新相关占用或汇总
```

两类锁的选型可以概括为：

```text
方法级防重复锁：
  业务方法开始前加锁
  方法结束后释放

业务实体状态锁：
  按实体标识显式获取
  完成状态修改和事务提交后释放
```

代码导读时优先从一个真实入口沿调用链向下追踪，并记录每一层的输入、输出和状态变化。直接通读整个模块容易把相似概念混在一起，也难以判断哪些结论已经由代码证实。
