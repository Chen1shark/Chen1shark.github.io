# 2026-08-03 工作日志：业务统计接口性能排查与优化实践

## 今日概览

对某业务统计系统的两个慢查询接口进行性能排查。通过 Arthas `trace` 拆分耗时后发现，主要瓶颈来自外部服务调用和全量数据处理；代码层面则存在可通过预聚合降低复杂度的局部热点。公开版本已移除真实业务名称、人员规模、环境耗时、组织口径和内部表结构。

## 完成事项

- 使用 `trace` 定位接口内各阶段的耗时占比。
- 将循环中的重复聚合改为循环前预聚合，复杂度由 O(N²) 降为 O(N)。
- 对 SQL 改写、分页下推和并行查询等方案分别评估收益与业务风险。
- 回退实测效果不佳的 SQL 改写，避免为“看起来更简洁”的查询付出额外成本。
- 记录可复用的性能诊断和方案取舍方法。

## 问题与解决

### 统计接口响应时间偏长

- **现象**：接口在数据量较大时响应明显变慢，且不同环境和时段波动较大。
- **分析**：外部服务调用占主要耗时；本地处理还存在对同一集合反复筛选和求和的问题。部分汇总字段依赖全量数据，因此不能直接把所有计算下推到分页之后。
- **处理**：在进入结果循环前按业务键预聚合所需指标，循环内通过 Map 常数时间读取；同时对候选 SQL 逐一实测，保留有效方案并回退负优化。
- **验证**：优化前后业务结果一致，本地计算耗时稳定下降；端到端耗时仍受外部依赖波动影响。

### 列表接口包含长时间范围的内存聚合

- **现象**：列表查询在读取较长时间范围数据后，还需要在应用内逐条累加。
- **分析**：这类计算更适合由数据库按业务键聚合，但是否改造取决于查询复用范围和数据口径。
- **处理**：设计按业务键 `GROUP BY` 的聚合查询，用条件聚合替代应用层长循环。
- **验证**：方案已完成静态核对，仍需在脱敏测试数据上比较结果一致性和执行计划。

### 架构图生成与校验

- **现象**：性能分析需要通过架构图和数据流图帮助说明调用边界。
- **分析**：图表应只呈现抽象组件和数据方向，不能带出内部服务名、域名或部署拓扑。
- **处理**：使用通用组件名生成架构图、数据流图和时序图，并进行格式校验。
- **验证**：图表可正常打开，且不包含可识别的内部信息。

## 技术记录

### O(N²) 聚合改为预聚合

```java
// 原写法：每个结果项都重新扫描集合
result.setTotal(source.stream()
    .filter(item -> Objects.equals(item.getGroupKey(), result.getGroupKey()))
    .mapToDouble(Item::getValue)
    .sum());

// 优化：先聚合，再按 key 查询
Map<Long, Double> totals = new HashMap<>();
for (Item item : source) {
    totals.merge(item.getGroupKey(), item.getValue(), Double::sum);
}
result.setTotal(totals.getOrDefault(result.getGroupKey(), 0D));
```

### 数据库条件聚合示意

```sql
SELECT group_key,
       SUM(CASE WHEN condition_a THEN value_a ELSE 0 END) AS metric_a,
       SUM(CASE WHEN condition_b THEN value_b ELSE 0 END) AS metric_b
FROM business_record
WHERE group_key IN (...)
  AND record_time >= :start_time
GROUP BY group_key;
```

性能排查时需要区分：

- 方法内部耗时与浏览器端到端耗时。
- 固定成本、随数据量线性增长的成本和 O(N²) 成本。
- SQL 语法简化与真实执行计划改善。
- 技术上可行与业务口径允许之间的差异。

## 今日总结

本次排查再次说明：性能优化应先用数据确认瓶颈，再评估每个方案的收益、风险和业务约束。预聚合是明确且低风险的改进；SQL 重写、并行化和分页下推则必须以执行计划和结果一致性验证为前提。
