## 问题与解决

### 返回模型字段遗漏导致编译失败

- **现象**：业务代码调用了某统计字段的 setter，但返回模型中只有说明注解，没有对应成员变量。
- **分析**：注解不会自动生成字段；代码生成工具只能为实际存在的成员变量生成访问方法。
- **处理**：补齐字段，并逐项核对返回模型与赋值代码的一致性。
- **验证**：静态核对通过，完整编译待验证。

### 自定义 SQL 未自动应用逻辑删除条件

- **现象**：框架生成的查询会过滤已删除数据，手写聚合查询却可能把这些数据统计进去。
- **分析**：逻辑删除条件通常由 ORM 框架注入到其生成的方法；手写 SQL 和自定义条件片段不一定经过相同处理。
- **处理**：调用自定义聚合方法前显式追加有效数据条件，使列表统计与导出口径一致。
- **验证**：代码路径已修正，运行结果待验证。

### 导出指标重复且命名不准确

- **现象**：两个统计列使用相同条件，计算结果始终一致；其中一个比率名称与实际计算口径不符。
- **分析**：重复列无法提供额外信息，含义不准确的名称还会误导读者。
- **处理**：删除重复指标，并按照“完成数量占总数量”的真实含义统一命名。
- **验证**：字段和计算口径已静态复核，导出文件待验证。

### 聚合数值按字符串解析存在风险

- **现象**：聚合查询结果通过 `toString()` 后再使用整数解析方法转换。
- **分析**：不同数据库驱动可能返回不同的 `Number` 子类型，字符串形式也可能带小数位，直接解析容易抛出格式异常。
- **处理**：统一按 `Number` 接收并调用 `longValue()`。
- **验证**：转换逻辑已替换，边界数据测试待补充。

## 技术记录

手写聚合查询应显式补充业务有效性条件：

```java
query.eq(Entity::getEnabled, true);
List<Map<String, Object>> rows = mapper.aggregate(query);
```

聚合结果使用数值基类转换：

```java
private long toLong(Object value) {
    return value == null ? 0L : ((Number) value).longValue();
}
```

计算比率时应同时处理零分母和舍入规则：

```java
private String percentage(long total, long completed) {
    if (total == 0) {
        return "-";
    }
    return BigDecimal.valueOf(completed * 100)
            .divide(BigDecimal.valueOf(total), 0, RoundingMode.HALF_UP)
            + "%";
}
```
