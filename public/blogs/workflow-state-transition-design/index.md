# 2026-08-07 工作日志：业务流程状态流转设计

## 今日概览

围绕一个通用业务流程完成状态流转设计，重点厘清流程图、流程引擎和业务代码之间的职责边界。最终将主流程收敛为单向推进链，撤回、驳回、改派和删除等非正常流转由业务服务在运行时处理，使流程模型更容易理解和维护。

## 完成事项

- 将流程图调整为只表达正常推进路径，移除容易造成歧义的回退网关。
- 区分候选组、候选用户和单人处理三种任务分配方式。
- 明确撤回、驳回、改派和删除应根据目标状态选择不同的运行时操作。
- 核对流程定义标识、配置项和启动参数的一致性要求。
- 将初始化脚本调整为可重复执行的形式，并清理可能影响匹配的多余字符。

## 问题与解决

### 回退动作是否应该画入主流程

- **现象**：初版流程图使用条件网关表达撤回等操作，导致正常推进条件和外部干预动作混在一起。
- **分析**：正常推进由当前任务处理人完成任务触发；撤回或改派通常由其他授权用户发起，属于运行时干预。两类动作的触发主体和语义不同，不宜共用一条网关分支。
- **处理**：流程图仅保留正常状态链；撤回通过终止实例并恢复业务状态处理，驳回通过运行时回退处理，改派通过更新处理人后重新分配任务。
- **验证**：设计已完成静态复核，实际流程运行结果待集成环境验证。

### 处理人配置方式容易混淆

- **现象**：单人处理节点没有固定角色配置，容易误以为无法推进任务。
- **分析**：单人任务可以在上一步办理时动态写入处理人；候选组适合多人共享的任务池，两者不需要采用相同的配置方式。
- **处理**：共享节点使用候选集合，单人节点使用动态处理人变量；节点完成后由流程引擎沿正常连线推进。
- **验证**：配置关系已核对，运行验证待完成。

### 初始化配置重复执行可能产生脏数据

- **现象**：普通插入脚本重复执行时可能出现主键冲突或重复配置。
- **分析**：环境初始化脚本应具备幂等性，并确保流程标识在配置、模型和代码中完全一致。
- **处理**：改用数据库支持的幂等写入方式，并在写入前规范化字符串值。
- **验证**：脚本结构已检查，实际数据库执行待验证。

## 技术记录

流程建模可以遵循以下边界：

```text
正常推进：完成当前任务 -> 流程引擎沿连线进入下一节点
撤回：终止流程实例 -> 业务数据恢复到未提交状态
驳回：运行时回退到指定节点 -> 流程继续存在
改派：更新处理人变量 -> 重新分配当前任务
删除：按业务规则逻辑删除，并处理关联流程实例
```

处理人配置的一般选择：

| 场景 | 推荐方式 | 说明 |
|---|---|---|
| 固定单人办理 | `assignee` | 由流程变量动态注入用户标识 |
| 多人任务池 | `candidateUsers` | 任一候选人可领取或办理 |
| 按角色分组 | `candidateGroups` | 由角色或组织映射候选集合 |
