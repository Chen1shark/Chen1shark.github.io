# 2026-08-14 工作日志：列表行级操作权限机制辨析

## 今日概览

围绕“列表页面如何判断当前用户能否操作某一行”梳理权限模型，区分功能入口权限、数据范围权限和行级操作权限。结论是：页面入口权限不能替代具体记录的操作判断，按钮显隐应由记录状态和当前用户身份共同决定，并由服务端再次执行同等强度的授权校验。

## 完成事项

- 梳理列表接口中与操作判断相关的数据。
- 对比“当前处理人标识”和“身份布尔字段”两种下发方式。
- 明确功能权限、数据范围和行级操作权限的职责边界。
- 识别仅按显示名称比对用户身份可能产生的误判风险。
- 确认前端按钮显隐只用于交互提示，不能代替后端鉴权。

## 问题与解决

### 列表接口是否应该直接返回按钮集合

- **现象**：前端需要逐行显示不同操作，容易认为后端必须返回按钮名称列表。
- **分析**：按钮是界面表达，后端更适合返回稳定的业务事实，例如状态和当前用户是否具备某类身份。前端根据这些事实组合展示，能降低接口与界面文案的耦合。
- **处理**：保留状态和身份信息，由前端映射按钮；后端操作接口仍独立校验状态与身份。
- **验证**：通过接口模型和调用路径完成静态核对。

### 当前处理人和身份布尔字段如何选择

- **现象**：两种实现都能让全量列表逐条判断权限，但前端复杂度和准确性不同。
- **分析**：下发处理人名称需要前端比对并处理重名、任务池等特殊场景；后端按稳定用户标识计算布尔值，前端使用更简单，也更不容易误判。
- **处理**：新接口优先返回语义明确的布尔能力字段；如需解释原因，可额外返回当前阶段或权限来源，但不下发敏感的组织成员信息。
- **验证**：方案已完成设计复核，尚未进行统一改造。

### 功能权限与行级按钮容易混为一谈

- **现象**：用户拥有模块权限后，页面仍有部分记录不可操作，容易被认为是权限配置异常。
- **分析**：功能权限决定能否访问入口，数据范围决定能看到哪些记录，行级权限决定能对某条记录执行什么动作。三者解决的是不同问题。
- **处理**：将鉴权拆成三层，并在接口文档中明确每层输入和输出。
- **验证**：已通过控制器、列表查询和操作服务三个层次完成静态核对。

### 只在服务层硬编码角色存在维护风险

- **现象**：部分操作没有统一权限声明，而是在业务方法中直接判断若干角色。
- **分析**：分散的硬编码规则难以审计，也容易在新增角色或状态时遗漏。
- **处理**：当前仅记录风险；后续应将规则集中到权限策略或能力计算组件，同时保留服务端最终校验。
- **验证**：待评估统一改造范围。

## 技术记录

三层权限模型：

```text
功能入口权限：用户能否访问模块或调用某类接口
数据范围权限：用户能看到哪些记录
行级操作权限：在当前状态下，用户能对某条记录执行哪些动作
```

推荐的返回模型使用稳定、语义化的能力字段：

```json
{
  "state": "PROCESSING",
  "capabilities": {
    "canAssign": false,
    "canHandle": true,
    "canReview": false,
    "canCancel": false
  }
}
```

前端只负责据此展示；调用操作接口时，后端必须重新计算并校验相同规则，避免通过直接请求绕过限制。

## 今日总结

权限问题需要先明确控制对象：入口、数据范围还是单条记录操作。将三层职责拆开后，前后端边界会更清晰；其中最重要的安全原则是，按钮隐藏只改善交互，真正的权限判断始终必须由后端完成。
