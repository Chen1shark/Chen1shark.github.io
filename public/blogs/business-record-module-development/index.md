# 2026-08-17 工作日志：业务记录模块开发与排错

## 今日概览

围绕一个通用业务记录模块完成一轮功能迭代，重点处理删除授权、聚合详情、状态提交和并发防护。代码评审还发现了两个容易被忽略的问题：辅助信息查询失败不应阻断主流程，空字符串可能绕过 ORM 的空值策略并覆盖已有文本。公开版本只保留通用设计思路，已移除真实业务名称、字段名、接口路径和内部模块关系。相关修改已完成静态检查，实际编译与联调结果待确认。

## 完成事项

- 为删除操作补充记录归属和业务状态校验。
- 梳理详情页面字段来源，将分散的展示信息收敛到聚合详情模型。
- 新增状态提交能力，并通过条件更新避免重复处理。
- 将非关键的辅助信息查询改为可降级处理。

- 同步更新设计说明，使需求口径与代码实现保持一致。

## 问题与解决

### 详情字段分散在多个数据来源

- **现象**：详情页面需要的展示字段多于基础记录本身包含的字段，前端需要组合多次查询结果。
- **分析**：基础记录只保存稳定关联标识，关联对象的展示名称来自其他数据源。若继续由前端拼装，容易造成契约分散和错误处理不一致。
- **处理**：保持基础模型不变，增加聚合详情模型，由服务层统一补充展示字段。
- **验证**：已完成静态核对；聚合详情能否覆盖页面全部字段待联调确认。

### 辅助查询失败导致详情不可用

- **现象**：用于补充展示信息的远程查询异常时，整个详情请求随之失败。
- **分析**：辅助字段不影响主体记录的真实性，不应拥有阻断详情的能力。
- **处理**：对辅助查询增加异常隔离和上下文日志，失败时返回空的辅助字段，主体详情继续返回。
- **验证**：异常降级逻辑已完成静态检查；远程服务不可用场景待验证。

### 空字符串覆盖已有展示文本

- **现象**：表单只提交选项标识、文本字段为空字符串时，已有文本可能被覆盖为空。
- **分析**：常见 ORM 更新策略会忽略空值，但通常不会自动忽略空字符串，因此空字符串仍会进入更新语句。
- **处理**：以稳定标识作为必填依据；文本缺失时根据标识补齐，标识无效则拒绝提交。
- **验证**：处理逻辑已完成静态检查；空字符串、无效标识和正常提交三类场景待验证。

### 重复提交造成状态竞争

- **现象**：并发请求可能同时读取到可处理状态，并重复执行状态提交。
- **分析**：仅在更新前查询状态不能保证并发安全，检查与更新之间仍存在时间窗口。
- **处理**：把预期状态放入更新条件，只有第一条请求能够成功修改；其他请求根据受影响行数返回冲突提示。
- **验证**：条件更新逻辑已完成静态检查，并发请求场景待验证。

## 技术记录

状态变更可抽象为带前置条件的原子更新：

```java
boolean updated = repository.updateStatusIfMatches(
    recordId,
    Status.PENDING,
    Status.PROCESSING
);

if (!updated) {
    throw new BusinessException("当前状态不允许重复处理");
}
```

这一方式不依赖额外的分布式锁，适合单条记录的简单状态竞争。它不能替代所有并发控制；若一次操作跨多条记录或多个外部系统，仍需结合事务、幂等键或更高层的协调机制。

更新接口还需要明确区分三种语义：空值表示“不修改”、空字符串表示“清空”，还是两者都视为缺失。若前后端没有统一约定，文本字段很容易出现意外覆盖。
