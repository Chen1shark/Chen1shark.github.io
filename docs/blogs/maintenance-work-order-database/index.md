# 2026-08-05 工作日志：业务工单模块的数据建模实践

## 今日概览

围绕一个通用业务工单模块完成需求澄清和数据模型设计。重点梳理了“模板—实例—执行记录”的关系、审计字段与业务字段的边界，以及工作流审批信息的存储职责。文中仅保留可复用的建模方法，不包含真实表名、字段清单、组织信息或内部流程配置。

## 完成事项

- 将数据模型拆分为工单主体、模板定义、模板明细、执行明细和节点处理记录等职责清晰的部分。
- 使用快照保存工单创建时的模板内容，避免模板更新影响历史记录。
- 区分通用审计字段和具有明确业务含义的人员字段。
- 将审批历史交由工作流能力管理，业务表只保留必要的关联标识。
- 采用可重复执行的初始化方式，降低多环境部署风险。

## 问题与解决

### 模板定义与执行记录边界不清

- **现象**：需求同时包含模板维护、文件上传和逐项执行，初期容易把定义数据与运行数据放入同一张表。
- **分析**：模板会被复用和更新，执行记录则必须长期保持创建时的业务语义，两者生命周期不同。
- **处理**：采用“模板主数据—模板条目—执行快照”三层结构，在创建工单时复制必要字段形成快照。
- **验证**：通过模板更新、历史查询和重复执行等场景检查，历史工单不依赖模板当前状态。

### 上传文件的存储职责

- **现象**：业务需要保留上传原文件，同时还要解析其中的结构化条目。
- **分析**：文件本体和解析结果用途不同；文件用于下载与留档，解析结果用于查询和执行。
- **处理**：文件交由统一文件能力保存，业务数据只记录文件引用；解析后的条目进入模板明细。
- **验证**：设计上可以分别支持原文件下载、条目查询和模板版本留痕。

### 审计字段与业务角色混用

- **现象**：创建人、操作人等审计信息容易被直接当作申请人、处理人等业务角色使用。
- **分析**：审计字段服务于数据追踪，业务角色服务于流程判断，二者含义和变更规则不同。
- **处理**：审计信息使用统一基类维护；只有流程确实需要的角色才建立业务字段或节点记录。
- **验证**：逐项检查字段是否参与业务规则、权限判断或历史追踪，删除无明确用途的重复字段。

### 审批信息重复存储

- **现象**：初版设计尝试在业务主表中保存完整审批历史。
- **分析**：审批历史已经由工作流能力维护，重复保存会带来一致性和扩展性问题。
- **处理**：业务表仅保留关联工作流实例所需的标识；节点处理信息按业务查询需要最小化保存。
- **验证**：确认审批历史可以通过工作流接口查询，业务数据无需复制完整流程记录。

## 技术记录

### 模板与实例的通用分层

```text
模板定义
  └─ 模板条目

业务实例
  └─ 执行条目快照
```

快照并不是无意义冗余。只要历史记录必须保持创建时语义，就应复制必要的名称、类型和规则；仍需实时变化的数据则通过关联查询获取。

### 幂等初始化原则

- 创建对象前检查是否存在。
- 初始化字典或配置时使用稳定业务键。
- 新增索引和字段时先检查元数据。
- 不在公开文档中保留真实表名、字段名和初始化数据。

## 今日总结

本次工作的核心不是增加表的数量，而是根据数据生命周期划分职责。模板、执行快照、审计信息和审批历史各自归属明确后，模型更容易扩展，也能减少重复字段和跨系统数据不一致的问题。
