## 问题与解决

### 维修工序模板与工序表概念辨析

- **现象**：业务方同时提到"维修工序模板""维修工序表""上传 Excel"，三者关系不清晰，导致表设计反复。
- **分析**：与业务方确认后明确——模板是全局统一维护的工序清单（上传一次，其他禁用旧的），工序表是某个具体工单实际执行的记录。与项目内已有的"巡检模板 + 模板条目"是同一套"模板—实例"模式。
- **处理**：将设计拆为三层——模板主表、模板明细表、执行明细表，执行明细在工单创建时复制模板明细作为快照，避免模板后续变更影响已执行工单。
- **验证**：与业务方逐项确认需求后落地建表，待带教审批。

### Excel 原文件的存储方式选择

- **现象**：业务上要求用户上传的工序 Excel 之后可下载，需要确定存储方案。
- **分析**：项目内文件类通常走对象存储（MinIO）存文件、表里存文件标识；但项目已有表用 `longblob` 直接存二进制（如模板文件），且本业务 Excel 仅为十几行小文件。
- **处理**：采用 `longblob` 存 Excel 原文件到模板主表，上传时字节流既用于解析又用于留档，与项目既有做法一致。
- **验证**：确认项目内已有多处 `longblob` 用法后采用，待验证实际下载链路。

### 创建人（审计字段）与业务人的字段区分

- **现象**：最初把主表的"创建人"字段直接用作"申请人"，且模板表同时建了"上传人"和"创建人"，字段语义冲突。
- **分析**：项目里 `create_user`/`update_user` 是公共逻辑自动填充的通用审计字段，不应承担业务角色；业务上的申请人、上传人若与创建人是同一人，直接用审计字段即可，不必重复建字段。
- **处理**：模板表删除重复的"上传人"字段，仅保留创建人；主表创建人注释明确为"创建人/申请人"，不再单独建申请人类字段。
- **验证**：与故障工单模块的字段惯例对齐，待代码实现时确认自动填充逻辑。

### 部门字段的取舍

- **现象**：最初给所有人字段都配了部门，但审计字段（创建人）本不该带部门。
- **分析**：参考故障工单——创建人是审计字段不带部门；分配人、维修人、审批人等业务角色带部门。同时业务上"无需问责申请人"，申请人部门无记录必要。
- **处理**：创建人不带部门；业务角色（分配、维修、审批）带部门。后续按带教意见调整后，分配人与审批人移入节点处理人子表，仅维修人保留在主表并带部门。
- **验证**：字段设计符合业务与项目惯例，待带教确认。

### 带教反馈：审批相关结构调整

- **现象**：带教指出分配人和审核人可能是多个，后续可能增加审批节点，仅靠主表各一个字段无法支撑；且审批记录应由工作流服务接口返回，不需要自行存储。
- **分析**：项目已接入工作流服务，通过流程实例标识可查询审批记录与审批人信息；多节点、多处理人需要独立子表承载。
- **处理**：① 新增节点处理人子表（节点类型 + 处理人 + 部门 + 处理时间 + 意见），主表只保留"最近一个节点审批人"快照；② 主表增加流程实例标识字段，删除审批意见、审批时间等字段，改从工作流接口读取；③ 维修人因业务特殊保留在主表。
- **验证**：确认项目内工作流接口可返回历史任务与审批人后完成调整，待带教复审。

### 故障现象数据类型的挂载问题

- **现象**：带教指出故障现象初始化数据中引用的"板卡类型"字典与既有"设备类型"字典不一致，界面展示可能异常。
- **分析**：故障现象表已有"设备类型"字段指向设备类型字典，向其写入自建的板卡类型值属于数据挂载位置错误。
- **处理**：暂保留初始化数据，待与产品确认故障现象应挂载到哪个维度后再调整。
- **验证**：待确认，未处理。

## 技术记录

### 数据库初始化脚本的幂等写法（项目惯例）

脚本整体使用 `IF NOT EXISTS`、`REPLACE INTO`、以及自定义的幂等加索引/加列存储过程，保证重复执行不报错。索引新增统一使用 `ALTER TABLE ... ADD INDEX` 形式。

### 表设计的分层模式

"模板主表 — 模板明细表 — 执行明细表"是项目内成熟的分层模式：模板定义可复用的工序清单，执行明细在工单创建时复制模板内容作为快照。快照字段（名称、类型等）看似冗余，实为避免模板后续变更影响历史工单。

### 审计字段与业务字段的区分原则

`create_user`/`update_user` 是自动填充的通用审计字段，不带部门；分配人、维修人、审批人等业务角色字段才携带部门。快照与冗余的判断标准是"数据是否只读"：只读数据（模板、用户、字典）做快照必要，可变数据（工单状态）做快照才叫冗余。
