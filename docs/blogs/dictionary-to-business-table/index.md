# 2026-08-13 工作日志：配置字典迁移为独立业务表

## 今日概览

将一个逐渐具备创建归属、启用状态和关联数据管理需求的配置项，从通用字典迁移为独立业务表。改造覆盖数据模型、管理接口、名称翻译和关联校验，同时保持主业务数据继续存储稳定编码，以降低迁移成本。

## 完成事项

- 设计独立业务表并准备初始数据迁移脚本。
- 新增创建、分页查询、启用和禁用等管理能力。
- 将批量名称翻译从字典查询切换为业务表映射。
- 为业务编码增加存在性校验和关联一致性校验。
- 在创建新分类时初始化必要的默认关联项。
- 区分“启用状态”和“逻辑删除”两种不同语义。

## 问题与解决

### 通用字典无法承载完整业务属性

- **现象**：配置项需要记录创建人、创建时间和可恢复的启用状态，但原字典模型无法稳定表达这些信息。
- **分析**：当数据开始拥有独立生命周期、管理接口和关联关系时，它已不再是简单的静态枚举。
- **处理**：迁移为独立业务表，保留稳定编码、名称、审计信息和启用状态；主业务表继续存储编码，避免大范围修改历史数据。
- **验证**：模型和脚本已完成静态检查，实际迁移结果待验证。

### 新分类缺少配套的默认关联项

- **现象**：创建新分类后，依赖该分类的下拉选项为空，导致后续业务无法完整录入。
- **分析**：分类和默认关联项存在初始化依赖，仅创建主记录会留下不完整状态。
- **处理**：在同一事务内创建分类和默认关联项，任一步失败都整体回滚。
- **验证**：事务逻辑已实现，运行验证待完成。

### 编码有效性与关联一致性校验不足

- **现象**：接口只检查编码非空，无法阻止不存在的编码或不匹配的关联项进入数据库。
- **分析**：缺少存在性检查会导致名称无法翻译；缺少归属校验会产生跨分类错配。
- **处理**：保存前验证分类编码存在，并确认关联项属于所选分类。
- **验证**：校验路径已静态核对，需在数据迁移完成后执行集成测试。

## 技术记录

字典与业务表可以按以下标准选择：

| 判断维度 | 通用字典 | 独立业务表 |
|---|---|---|
| 数据是否近似静态 | 适合 | 均可 |
| 是否需要审计归属 | 能力有限 | 适合 |
| 是否有独立 CRUD | 不推荐 | 适合 |
| 是否存在复杂关联 | 不推荐 | 适合 |
| 是否需要禁用后恢复 | 视平台能力 | 可明确建模 |

批量翻译应先构建映射，避免循环查询：

```java
Map<String, String> nameByCode = repository.findAllReferencedCodes().stream()
        .collect(Collectors.toMap(Item::getCode, Item::getName));

for (Record row : records) {
    row.setCategoryName(nameByCode.get(row.getCategoryCode()));
}
```

历史记录的名称翻译通常应包含已禁用项；禁用只限制新选择，不应破坏历史数据展示。
