## 问题与解决

### 采集服务依赖哪些公共库模块及调用方式

- **现象**：接手既有采集服务，不清楚其依赖的平台公共库模块范围与调用方式。
- **分析**：通过 pom 依赖链与实际 import 语句交叉定位，采集服务直接依赖数据下发模块与某领域模块，经本地封装模块间接依赖协议封装、一致性哈希模块，再经传递依赖领域模型、公共基础、位置等模块。关键发现：实体 PO/枚举/事件类物理上集中在公共库的领域模型模块，但包名分属各业务模块，排查时易找错位置。
- **处理**：阅读公共库与采集侧源码，按"被依赖代码-采集调用代码-讲解"三段式整理为教学文档。
- **验证**：文档中每个调用点均标注文件路径与行号，可逐条核对。

### 切换环境是否等同于跑对应 yml 文件

- **现象**：误以为使用开发/测试环境实质就是运行 dev/test 的 yml 文件。
- **分析**：Spring profile 机制下，激活某 profile 后加载基础 application.yml 叠加 application-{profile}.yml；yml 只是指向基础设施（数据库/缓存/消息中间件地址）的配置指针，环境本身是背后那套基础设施。本项目还接入配置中心，部分配置不在本地 yml（如生产环境业务配置走配置中心下发）。本项目 profile 命名为 dev/pro 等，无 test。
- **处理**：概念澄清，说明三种激活方式（yml 写死、启动参数、环境变量）。
- **验证**：对照实际多环境配置文件确认各 profile 指向不同基础设施地址。待确认：是否存在独立测试环境。

### 本机是否为容器集群节点

- **现象**：误以为本机是某 k8s 集群中的一个节点。
- **分析**：集群是由一组机器组成、统一调度容器的系统；节点是机器，容器运行时是节点上运行容器的软件，二者概念不同。本机若为节点需运行 kubelet 并 join 到控制面。
- **处理**：执行只读检查（查找 kubelet/k3s/minikube 等进程，检查容器与 kubectl CLI 是否可用）。
- **验证**：确认本机无相关进程与 CLI，非集群节点，实为集群外客户端，通过应用进程连接集群暴露的服务端口。

### "采集依赖分析库"方向矛盾

- **现象**：直觉上应"先采集后分析"，但代码里采集依赖了某内部仓库（功能上属于分析库），方向看似矛盾。
- **分析**：该仓库实为平台 monorepo，同时包含基础库、分析库、处理服务、甚至采集变种代码。关键区分：代码依赖方向（编译期，采集与分析平级依赖公共底座）≠ 运行时数据流方向（采集 -> 消息中间件 -> 分析服务消费）。
- **处理**：梳理模块清单与启动类分布。
- **验证**：确认分析处理逻辑由独立处理服务运行，采集服务不依赖分析库模块。

### 读寄存器与一致性哈希环代码归属

- **现象**：不确定"读寄存器""哈希环"等底层能力在采集仓库还是公共库。
- **分析**：按文件路径定位，二者均在公共库；采集仓库仅在之上做业务封装（主从切换、轮询上下文、变化检测、采集类别枚举），最上层才是具体专业采集业务。
- **处理**：grep 定位采集侧调用底层读寄存器方法的位置。
- **验证**：确认采集侧调用该方法共两处，分别在批量读点位与读曲线方法中。

### 分页查询接口响应缓慢（约 5 秒）

- **现象**：测试环境反馈某分页查询接口耗时约 5 秒；本地（连开发库）仅约 1 秒，测试环境约 3 秒。
- **分析**：
  - 接口分页查询本身使用了"逗号分隔日期字段 + 数字辅助表拆行"的写法，会按日期数放大行数。但单独 COUNT 拆行结果仅数百行，SQL 本身耗时很低，排除 SQL 为当前环境主因。
  - 服务端日志显示总耗时随分页 size 线性增长（size=20 约 1.5s，size=1000 约 3.5s），说明耗时随返回记录数线性增加，指向"每条记录一次"的查询模式，即 N+1。
  - 分页结果填充明细时，对每条记录单独执行一次明细查询（`forEach` 内 `selectList(eq(...))`），N 条记录即 N 次数据库往返，顺序执行，叠加远程库网络延迟。
- **处理**：将 N 次逐条查询改为 1 次批量 IN 查询，再在内存按外键分组回填（关键代码见"技术记录"）。
- **验证**：改前 size=1000 实测约 3.5s；改后尚未在测试环境复测，**待验证**。

### 接口调用返回 423"未知异常"或"登录已过期"

- **现象**：联调时接口返回业务码 423"未知异常"或"登录已过期"。
- **分析**：
  - 服务端日志显示：请求未携带有效鉴权头时，鉴权拦截器抛出"登录已过期"；请求体为空时抛出"Required request body is missing"，被全局异常处理器兜底为 423"未知异常"。
  - 该服务鉴权外包给独立认证中心，私有接口需在请求头携带 ID-Token；本地若开启本地免鉴权模式可放行无权限注解的接口。
- **处理**：在接口测试工具中为环境配置 ID-Token 请求头（测试环境使用真实令牌），请求体使用 JSON 传分页参数。
- **验证**：配置后接口可正常返回业务数据。

```text
环 = 按 hash 排序的有序映射

查归属：dataKey 的 hash -> 环上顺时针最近虚拟节点 -> 其物理节点
        超过环尾则回绕到环首
重建时机：成员列表变化时重建（事件驱动 + 按需）
```

N+1 改批量查询（伪代码）：

```java
// 改前：N+1，每条记录单独查明细
records.forEach(r -> {
    List<Detail> details = detailMapper.selectList(eq(Detail::getFid, r.getId()));
    r.setDetails(details);
});

// 改后：一次 IN 查询 + 内存分组回填
List<Long> ids = records.stream().map(Rec::getId).collect(Collectors.toList());
List<Detail> all = detailMapper.selectList(in(Detail::getFid, ids));
Map<Long, List<Detail>> map = CollUtil.isEmpty(all)
        ? Collections.emptyMap()
        : all.stream().collect(Collectors.groupingBy(Detail::getFid));
records.forEach(r -> r.setDetails(map.getOrDefault(r.getId(), new ArrayList<>())));
```

"逗号分隔字段拆行"SQL 模式（抽象）：

```sql
SELECT DISTINCT <字段>
FROM (
  SELECT a.*, SUBSTRING_INDEX(SUBSTRING_INDEX(b.date_csv, ',', c.id), ',', -1) AS split_date
  FROM 主表 a
  LEFT JOIN 明细表 b ON a.id = b.fid
  JOIN 数字辅助表 c
  WHERE c.id <= LENGTH(b.date_csv) - LENGTH(REPLACE(b.date_csv, ',', '')) + 1
) t
ORDER BY t.update_time DESC
LIMIT 0, 100
```

- `LENGTH(s) - LENGTH(REPLACE(s, ',', '')) + 1` 计算逗号分隔串中的值个数；`JOIN 数字辅助表` 按该数量放大行数，再用双层 `SUBSTRING_INDEX` 取出第 n 个值。
- 该写法会在派生表上产生 DISTINCT 加 filesort，且 LIMIT 最后才生效，数据量增大后易慢。

定位 N+1 的变量控制法：

- 固定其它条件，仅改变分页 `size`（如 20/100/500/1000），观察总耗时变化。
- 线性增长说明主因为"每条记录一次"的查询（N+1）；基本不变说明主因为固定开销（如远程调用、主查询）。
- 斜率约等于单条 N+1 往返耗时，截距约等于固定开销。
