## 问题与解决

### 如何判断服务真正依赖的模块

- **现象**：依赖树中包含大量传递依赖，仅看构建文件难以判断实际使用范围。
- **分析**：声明依赖表示编译可见，导入语句和调用点才表示业务代码真实使用；运行时消息流又是另一层关系。
- **处理**：交叉检查依赖树、导入语句和调用位置，并用“调用方—抽象能力—运行服务”三层方式记录。
- **验证**：每个结论都可以通过通用调用关系复核，公开版本不保留内部路径和模块名。

### Profile 与运行环境概念混淆

- **现象**：容易把“启用某个 Profile”理解为直接运行对应的 YAML 文件。
- **分析**：Profile 决定加载哪些配置；真实环境由这些配置所指向的数据库、缓存、消息系统等资源共同组成。
- **处理**：梳理基础配置、环境覆盖配置、启动参数和环境变量之间的优先关系。
- **验证**：使用本地模拟配置验证不同 Profile 会加载不同属性组合。

### 代码依赖方向与数据流方向不一致

- **现象**：从仓库结构看，两个服务都依赖公共能力，容易误判为其中一个业务服务依赖另一个。
- **分析**：编译期依赖表示代码复用，运行时数据流表示消息或请求的传递方向，二者不能混为一谈。
- **处理**：分别绘制编译依赖图和运行时数据流图。
- **验证**：抽象图可以清楚表达公共底座和上下游数据关系，同时不暴露内部服务名称。

### 分页接口响应随记录数增长

- **现象**：增加分页大小后，接口耗时近似线性增长。
- **分析**：主查询完成后，循环内为每条记录查询一次明细，数据库往返次数随记录数增加。
- **处理**：一次收集所有主键，批量查询明细，并按外键在内存中分组回填。
- **验证**：代码路径由 N 次明细查询变为固定次数查询；实际耗时仍需在脱敏测试数据上复测。

### 接口联调返回认证或参数错误

- **现象**：接口返回认证失败，缺少请求体时又被统一异常处理转换成通用错误。
- **分析**：认证信息和请求体校验发生在不同阶段，不能仅凭最终业务码判断根因。
- **处理**：先确认请求方法、Content-Type 和 JSON 请求体，再通过受控测试凭据验证认证链路；公开文档不记录真实令牌、请求头名称或免认证开关。
- **验证**：在隔离测试环境中，请求格式和认证信息正确后接口可以正常响应。

## 技术记录

### 三层能力边界

```text
业务编排层
    ↓
通用封装层
    ↓
协议与基础能力层
```

### 代码依赖与运行时数据流

```text
编译期：服务 A ─┐
               ├─> 公共能力
        服务 B ─┘

运行期：服务 A ──消息或请求──> 服务 B
```

### N+1 改为批量查询

```java
List<Long> ids = records.stream()
    .map(Record::getId)
    .toList();

List<Detail> allDetails = detailRepository.findByParentIds(ids);
Map<Long, List<Detail>> grouped = allDetails.stream()
    .collect(Collectors.groupingBy(Detail::getParentId));

records.forEach(record ->
    record.setDetails(grouped.getOrDefault(record.getId(), Collections.emptyList()))
);
```

### 定位 N+1 的变量控制法

- 固定筛选条件，只改变分页大小。
- 若耗时近似线性增长，重点检查循环内查询和逐条远程调用。
- 若耗时基本不变，重点检查主查询、固定远程调用或序列化成本。
- 使用 SQL 日志验证，不只依赖接口总耗时推断。

### 多值字段拆行的通用风险

```sql
SELECT DISTINCT <columns>
FROM <main_table>
JOIN <detail_table> ON <join-condition>
JOIN <sequence_table> ON <split-condition>
ORDER BY <sort-column>;
```

多值字符串拆行会放大中间结果，并可能引入临时表、去重和排序成本。更长期的方案通常是规范化关联表或数据库原生结构化类型。
